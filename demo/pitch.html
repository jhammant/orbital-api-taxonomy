The problem

Every cross-system question
is an integration project.

"Give me a full profile of this company — who they are, where they are, the risk & context around them." In most companies that's a two-quarter project: five teams, five API contracts, brittle glue, a new pipeline, and a data model nobody agrees on. Add a sixth source — start over.

Old way · iPaaS / ETL

O(N²)

A human pre-wires every A→B connection. N sources → N² brittle connectors to build and maintain. Data is copied on a schedule and goes stale. New source = new pipeline.

The tax

“We can’t
answer that.”

Integration sprawl makes the platform team the bottleneck every other team complains about — and every new question waits in their backlog.

Orbital · semantic router

O(N)

Describe each source once by the meaning of its data. Orbital derives the call graph at query time. The Nth source is instantly reachable from every existing query.

The thesis

Route data by meaning,
not by plumbing.

  • 01
    Shared semantic types. Describe each API's inputs & outputs with a common vocabulary — Postcode, Latitude, CompanyName, Ticker.
  • 02
    Describe, don't integrate. A few lines of Taxi per source. No point-to-point code between any two services — ever.
  • 03
    Query-time composition. Orbital matches one operation's output type to another's input and plans the multi-API call graph itself.
  • 04
    Lineage as proof. Every assembled answer ships with a deterministic, auditable graph of exactly how it was built.
The whole idea
One engine.
One spine.
Every domain.

A company links to its ticker, its filings, its people, its repos — all the same entity, answerable as one.

Why it compounds

One tiny adapter fused two whole clusters.

The model had an identity cluster (company registries, emitting a postcode) and a geo cluster (crime, flood, weather, transit — all keyed on coordinates) that never touched. One ~30-line adapter — Postcodes.io, turning a postcode into coordinates — became the single edge that connected them.
